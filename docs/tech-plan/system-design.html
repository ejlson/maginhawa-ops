How a request travels from a site's iPad to SharePoint

Every request goes from the app on the device, through one of our Netlify Functions, to SharePoint via Microsoft Graph. Devices never talk to SharePoint directly. Several people can work on the same report or checklist at once.

What happens on every request

  1. The device sends the change with the person's sign-in tokenThe token comes from Entra ID. It also says which version of the record the device started from.
  2. The function checks who is callingThe name and role come from the token, never from the request. Someone can only reach their own sites. Otherwise they get 403.
  3. The function checks the figures with packages/coreThe same code the app uses. Totals are worked out again on the server, and the device's totals are only for display.
  4. It writes to SharePoint only if nothing changed in betweenGraph write with If-Match on the item's ETag. If someone saved first, the answer is 409, and the device merges and tries again.
  5. Then any follow-up runsThe finance email or the PDF. The report is already saved, so if the email fails, the manager doesn't have to submit again.

Working together live

Several people can fill in the same EOD report or checklist from different devices at the same time. Each device shows its own edits straight away. Every ~10 seconds while the screen is on, it asks the server what changed, and again whenever the app comes back into view or the signal returns.

EOD report: one record, merged by section

  • The whole day is one TradingDays item with a version (its ETag). Every save says which version it started from.
  • If someone saved in between, the server answers 409 with what is stored now. The device merges the 8 sections: Lunch, Dinner, Delivery, Promotions, Wages, Tips, Feedback, Handover.
  • Different sections merge on their own. "Jo changed Dinner at 21:14" appears, and nothing is lost.
  • Only the same section changed by two people is a clash. The person picks which version to keep.
  • Incoming changes never overwrite the section you are typing in.
  • Submit is one conditional write. The second person sees "Already sent by Jo at 23:48".

Checklists: one record per answer

  • Each answer is its own Responses row (run + checkpoint). Two people ticking different items never clash.
  • The same item: the latest answer wins, by when it was answered. A phone coming back online can't overwrite a newer answer.
  • The screen shows who answered each item.
  • Finish is conditional. The second Finish does nothing and shows "Submitted by Jo at 21:02".
  • After Finish, only supervisors and above can correct an answer, with a reason. The old answer stays on record.
  • Answers go in batches, and polling asks for changes since a cursor.

Rate limits

The app keeps its own request count low on the device. Nothing yet limits requests on the server, and Microsoft's throttling isn't handled in code.

What to add before going live

  • Graph wrapper: on 429 or 503, wait for Retry-After, then retry up to 3 times. If it still fails, return 503 with Retry-After to the device. The work is already saved on the device, so nothing is lost.
  • Device backoff with jitter: after failures, wait 10 s, then 20 s, 40 s, up to 2 min, plus a random 0–3 s. This stops 8 sites retrying in step around 23:00.
  • Per-user limit in the functions: for example 60 writes and 30 polls a minute per person, counted in Netlify Blobs. Above that, return 429 with Retry-After.
  • Version cache: keep each site's current version in Blobs, so a poll that finds nothing new never reaches Graph.
  • PIN tries on the server once Entra and SharePoint are connected, so clearing the device can't reset them.
  • Cap clash retries at 3, then ask the person.

Status and weak spots

1
Rules are built and tested, but not connected yetMerging, conditional writes and batching run in packages/core and are tested with two clients sharing one store. The functions answer 503 until Entra ID and SharePoint are connected. Until then the app runs in demo mode on the device.
Not live yet
2
Live means about 10 seconds, not instantIt's polling, not push. Azure Web PubSub can replace it later through the LiveTransport interface, without changing any screens.
By design
3
Polling is most of the trafficEach site's current version is kept in Netlify Blobs, so a poll with nothing new never reaches Graph (at most one check per site per minute). Screens left untouched poll every 30 s instead of 10 s.
Built
4
SharePoint can't make a batch all-or-nothingThe in-memory store applies a batch atomically, but a Graph $batch isn't a transaction. The SharePoint store needs If-Match on each answer, and a unique Title on ChecklistRuns and Responses so two devices can't create the same run twice.
Design for it
5
"Latest answer wins" uses the device's clockA device with the wrong time could win or lose unfairly. Fix: stamp the time on the server, keeping the device time only for answers that were queued offline.
