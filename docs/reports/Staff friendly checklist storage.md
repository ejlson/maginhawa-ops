# Store checklists in lists, file them for people

*Research report, 9 November 2026. Builds on the 6 November report on SharePoint checklist data storage and supersedes it where the two differ. All volumes, sizes, timings and site names are examples or estimates, not real Maginhawa data. Claims are **verified** (official source linked), **community** (forum, vendor or trade body), or **recommendation** (our reasoning). Fixed decisions are not reopened: SharePoint is the store, our Netlify Functions are the back end, we code our own React Router v7 app, managers type figures in, and Power Automate is only an optional add-on.*

The most efficient, effective and staff-friendly method is a split. Our app writes every checklist into **SharePoint lists** (the system of record, as already planned). A background function then **files a human copy** of each finished day into a new **"Maginhawa App Checklists" library with one folder per restaurant**: a read-only PDF per site per day, plus one Excel workbook per site per month that is rebuilt nightly. Excel cannot be the store. Microsoft's own reference page lists **application permissions as "Not supported"** for adding table rows ([Graph: TableRowCollection add](https://learn.microsoft.com/en-us/graph/api/tablerowcollection-add?view=graph-rest-1.0)), and our functions run app-only. Microsoft also tells developers to send one request at a time to each workbook ([Excel API best practices](https://learn.microsoft.com/en-us/graph/workbook-best-practice)), which does not suit several staff saving at once. Raw files in folders cannot be the store either. A library is a list underneath, with the **same 5,000-item view threshold and 20-index cap** ([Microsoft Support](https://support.microsoft.com/en-us/office/add-an-index-to-a-list-or-library-column-f3f00554-b7dc-44d1-a2ed-d477eac463b0)), and answers locked inside files cannot be filtered or totted up. The folders are still worth having as the place where people *find* things: a manager taps "Bunso › 2026-11" on an iPhone and opens a PDF, head office opens a monthly workbook, and an EHO gets a view-only expiring link or an emailed PDF. Staff never see SharePoint at all. They see a timeline of small checks in our app. This mirrors how the UK market leader structures its product ([Trail](https://trailapp.com/lp/digital-restaurant-checklist)). Four facts from the earlier plan change. Netlify's synchronous limit is **60 seconds**, not about 10 ([Netlify](https://docs.netlify.com/build/functions/configuration/)). SharePoint Online can **block index creation once a list passes 5,000 items**, so indexes must exist before the first row. Graph Excel row-add is delegated-only. Monthly exports should be **XLSX, not CSV**.

## Excel fails as a store but works well as a view

The question "could it just live in a spreadsheet?" has a clear answer, and the reason is permissions, not size. Maginhawa's functions call Microsoft Graph **app-only with Sites.Selected**. The permissions table for `workbook/tables/{id}/rows/add` reads "Application: Not supported" (page updated 19 May 2026) ([Graph: TableRowCollection add](https://learn.microsoft.com/en-us/graph/api/tablerowcollection-add?view=graph-rest-1.0)). A Microsoft Q&A answer confirms that app-only read and write of shared Excel files is unsupported ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2286958/support-required-for-shared-excel-file-read-write)). The only way round it would be a "service user" with stored delegated tokens. That means refresh tokens kept in Netlify, MFA and conditional-access exceptions, and a break from the agreed architecture.

Even with delegated access, the workbook API is built for one writer. Microsoft writes that "for each workbook, only send the next request after receiving a successful response to the current request". It warns that concurrent writes cause "throttling, timeout… merge conflict and other types of failures", and that after a failure "there is no way to confirm the status of other pending requests" ([Excel API best practices](https://learn.microsoft.com/en-us/graph/workbook-best-practice)). A lock error, `accessConflict`, is documented as a normal case when "another client has locked the workbook for edit". In practice, a manager with the file open in desktop Excel can block the app ([Excel API error handling](https://learn.microsoft.com/en-us/graph/workbook-error-handling)). Excel rows also have no ETag, so the `If-Match` optimistic concurrency that the whole sync design relies on cannot work. Community threads report **persistent 504 time-outs** on row adds that grow with table size, and in one case the only fix was deleting historic rows ([Q&A 1365864](https://learn.microsoft.com/en-us/answers/questions/1365864/persistent-504-errors-in-excel-operations-with-mic); [Power Users forum](https://powerusers.microsoft.com/t5/General-Power-Automate/Power-Automate-Gateway-Error/m-p/1995360/highlight/true)). One master workbook would collect about 410,000 answer rows a year (estimate), which is the "large, slow, recalculating" pattern behind those reports.

Excel does work well as something people *read*, as long as it is written as a whole file and not row by row. Uploading a complete file with `PUT …/content` supports application permissions and files up to 250 MB ([Graph: upload small files](https://learn.microsoft.com/en-us/graph/api/driveitem-put-content?view=graph-rest-1.0)). A function can therefore build each site's monthly workbook in Node with ExcelJS from the list data, and replace the old file. **Recommendation:** rebuild it once a night (and on demand), rather than appending to it. A rebuild is idempotent and repairs itself, so if one night fails, the next night's file is correct again. Two cautions apply. Every upload creates a new file version, so set the library's version limits on purpose. Microsoft's Automatic setting thins versions over time and cuts version storage by about 94–96% ([Plan version storage](https://learn.microsoft.com/en-us/sharepoint/plan-version-storage)). And replacing a file that carries a sensitivity label is not supported app-only ([Graph: upload small files](https://learn.microsoft.com/en-us/graph/api/driveitem-put-content?view=graph-rest-1.0)), so keep labels off this library. XLSX beats the earlier plan's CSV for non-technical readers. A CSV opened on an iPhone loses formatting and can misread UK dates, while an XLSX can have typed dates, a frozen header row and a filterable Excel table (community: [npm-compare](https://npm-compare.com/exceljs,xlsx)).

For head office on a laptop, a live option sits alongside the static workbook. Excel for the web can now refresh Power Query from a **SharePoint Online list** (announced July 2025) ([Tech Community](https://techcommunity.microsoft.com/t5/excel-blog/new-in-excel-for-the-web-power-query-refresh-data-source/ba-p/4422757)). The native Excel app on iPad and iPhone cannot refresh connections, though (community: [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5780996/data-refresh-functionality-in-excel)). The list's own "Export to Excel" downloads a one-way `.iqy` query that does not work on Mac ([Microsoft Support](https://support.microsoft.com/en-gb/topic/can-t-export-a-sharepoint-list-to-excel-for-mac-641b0eab-2b7d-490e-9f42-c216b053edb9)). CSV export from a list stops at 30,000 rows ([Microsoft Support](https://support.microsoft.com/en-us/office/export-to-excel-from-sharepoint-or-lists-bfb2ea48-6118-4fa9-abb6-cced9424e5d9)). So managers on phones get finished files, and only desk users get live queries.

| Option | Works app-only with Sites.Selected | Several staff at once | Find and report across sites | Staff-friendly to read | Verdict |
|---|---|---|---|---|---|
| Excel workbook as the store | **No** (row add is delegated-only) | One writer per workbook; lock and 504 errors | Good once written | Familiar | Rejected as a store |
| JSON/PDF file per checklist as the store | Yes | Whole-file read, merge and write, with no gain over a list column | Poor: each file must be downloaded | PDF yes, JSON no | Rejected as a store |

## A restaurant folder works as the filing cabinet, not the database

The folder idea earns its place for one reason: people understand it. MVP guidance agrees that metadata is better for filtering and views, folders are better for simple navigation and permission boundaries, and most good libraries use both (community: [SharePoint Maven](https://sharepointmaven.com/sharepoint-folders-vs-metadata/)). Folders count as items and do not raise the 5,000 threshold, but browsing inside one keeps each view small ([Microsoft Support](https://support.microsoft.com/en-us/office/manage-large-lists-and-libraries-b8588dae-9387-48c2-9248-c24122f07c59)). **Recommendation:** use a shallow tree, `Maginhawa App Checklists/{Restaurant}/{yyyy-MM}/`, with indexed metadata columns on every file: `SiteCode`, `BusinessDateKey`, `DayKey`, `Kind` (Day record / Month workbook / EHO pack) and `Status`. With one PDF per site per day, a month folder holds about 31 files plus one workbook (estimate). That is easy to scroll on an iPhone, and the whole library grows by about 3,000 files a year, against a 30-million-item limit ([SharePoint limits](https://learn.microsoft.com/en-us/office365/servicedescriptions/sharepoint-online-service-description/sharepoint-online-limits)). Indexed metadata still lets head office build a flat cross-site view ("every Missed day in October") without relying on the folder tree.

**One PDF per site per day, not per run.** The research notes priced a PDF per finished run at about 17,500 files a year. One per day keeps folders readable, matches the SFBB "diary page" an EHO expects, and lines up with the `ChecklistDays` header that already exists. The day PDF is built after the day closes and rebuilt if a correction is made. Graph sharing links always point to the current version of a file ([Graph: createLink](https://learn.microsoft.com/en-us/graph/api/driveitem-createlink)), and version history keeps the earlier copy. File names should read well in the iOS Files app, where only the name shows, for example `2026-11-09 Bunso daily checks - Submitted.pdf`. A day marked Missed or Not trading gets a one-page PDF that says so, so gaps are visible in the folder rather than shown only by a missing file.

**Generate PDFs in a background function with a pure-JavaScript library.** Puppeteer with Chromium adds about 50 MB to the deploy, takes 3–6 s to cold-start and needs 400–600 MB of memory. @react-pdf/renderer adds about 2 MB and produced documents in under 500 ms in one production comparison (community: [dev.to](https://dev.to/iurii_rogulia/pdf-generation-on-the-server-puppeteer-vs-react-pdfrenderer-a-production-comparison-44cg)). Because our app is React, react-pdf lets the PDF reuse the app's "premium" look. Graph's own `?format=pdf` conversion is not worth it: it caps the source file at **2 MB** and lists Files.ReadWrite.All as its least-privileged app permission ([Graph: convert format](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content-format)). Netlify background functions run for up to **15 minutes** but accept only a **256 KB** payload ([Netlify](https://docs.netlify.com/build/functions/configuration/)), so pass the `DayKey` and let the function read the answers itself. Embed photos as roughly 800 px thumbnails and link to the originals, so PDFs stay small.

**Who can change the folder.** Only the app identity writes. People get Read. **Recommendation:** break inheritance once per restaurant folder, so that site's managers and head office can read it. Nine unique permission sets sit well under Microsoft's recommended limit of 5,000 ([Microsoft Support](https://support.microsoft.com/en-us/office/manage-large-lists-and-libraries-b8588dae-9387-48c2-9248-c24122f07c59)). Month folders inherit. If the group is happy for every manager to see every site, skip the broken inheritance altogether (*open question for the user*). Photos stay in the existing `Photos` library, where the app serves them through our function under UK GDPR control. They are not loose files in the restaurant folders. *Agreed 9 Nov 2026:* the Photos library is foldered `{Restaurant}/{yyyy-MM}/{yyyy-MM-dd}/{Checklist name}/` with readable file names (`Walk-in chiller – 09:12.jpg`), so a checklist's photos sit together; the app still links by `PhotoId`, and photos are kept about 12 months unless tied to an incident (open decision).

## Staff finish faster when the checklist is a timeline of small checks

The products that UK restaurant groups actually use do not hand staff one long daily form. Trail, whose customers include Gail's, itsu and Zizzi, shows "a structured list of checks organised by time of day". Each check is signed off separately with a **six-digit personal PIN** on a shared device. Out-of-range readings are flagged at once and can require a linked corrective action before the task closes. Photo fields can be limited to **live camera capture**. Offline work syncs later with **device-time timestamps** ([Trail](https://trailapp.com/lp/digital-restaurant-checklist)). Food-safety specialists go further and remove typing altogether: Comark pairs a Bluetooth probe with its app ([TEquipment](https://www.tequipment.net/Comark/BT250KC/Contact-Thermometers)), and Checkit sensors replaced manual fridge checks at One Aldwych ([Checkit case study](https://www.casestudies.com/company/checkit/case-study/one-aldwych-takes-food-safety-into-the-21st-century)). Our earlier design already splits the day into per-template runs (opening, temperatures at set times, closing), so it matches this timeline model without any change to storage.

The evidence on layout is mixed, and it points to a grouped list. GOV.UK found one-thing-per-page easier on mobile ([GOV.UK design notes, 2015](https://designnotes.blog.gov.uk/2015/07/03/one-thing-per-page/)). Vendor tests found single questions win only for short forms of about three questions, with a single page holding up better for longer ones (community: [Starred](https://www.starred.com/fr/blog/feedback-form-page-evolution)). **Recommendation:** show each run as a grouped list with large tap targets, inline yes/no toggles and a numeric keypad for temperatures. Switch to a focused single screen only for a failure (corrective action), a photo, or the sign-off. Completion figures in vendor case studies, such as Culver's moving from about 20% to over 90% with Jolt ([Jolt case study](https://www.casestudies.com/company/jolt/case-study/jolt-increased-task-completion-rate-at-culvers-by-350)), are self-reported gains from weak paper baselines. They show direction, not a forecast. Staff complaints about the leaders concern speed, sync glitches and clunky mobile screens, not the idea itself. One Trail reviewer said reports can take up to 30 minutes to generate (community: [Capterra](https://www.capterra.co.uk/software/176765/trail)). That argues for pre-building the day PDF overnight rather than on request.

Microsoft Forms is no shortcut either. File upload works only for people inside the organisation ([Tech Community](https://techcommunity.microsoft.com/discussions/microsoftforms/file-upload-option-not-available-for-external-users-/4388010)), and users report photo upload failing on iPad (community: [Tech Community](https://techcommunity.microsoft.com/discussions/microsoftforms/failed-to-upload-a-file-ios-ipad-issue/4038801)). It has no PIN identity, no range checks and no offline mode, which supports coding our own app.

## Inspectors reward complete, honest records more than tidy ones

The law sets outcomes, not formats. Retained Regulation 852/2004 requires records "commensurate with the nature and size of the food business" and asks businesses to keep them "for an appropriate period" ([legislation.gov.uk](https://www.legislation.gov.uk/eur/2004/852/article/5)). The FSA says SFBB diary pages can be filled in and stored electronically "until your next visit" ([GOV.UK SFBB](https://www.gov.uk/government/publications/safer-food-better-business-sfbb/safer-food-better-business-sfbb)). For the hygiene rating, the records element of "confidence in management" matters most. Score 0 needs records "appropriate and maintained". Score 10 means "some deficiencies/gaps", and to reach a rating of 5, no element may score above 5 (community, reproducing the Code of Practice: [High Speed Training](https://highspeedtraining.co.uk/hub/wp-content/uploads/2025/03/fhrs-scoring-table.pdf); [Doncaster Council](https://www.doncaster.gov.uk/services/environmental/food-hygiene-rating-scheme)). One council's 2026 newsletter says officers "expect to see the entire SFBB pack, not just the diary pages", fully completed and organised, with opening and closing records done daily ([West Norfolk BC](https://www.west-norfolk.gov.uk/download/downloads/id/9885/special_edition_food_and_safety_newsletter_-_april_2026.pdf)). That supports putting the procedures, not only the records, into Inspection mode.

The due-diligence defence under the Food Safety Act 1990 s.21 requires the business to *prove* "all reasonable precautions and… all due diligence" ([legislation.gov.uk](https://www.legislation.gov.uk/ukpga/1990/16/section/21)). Trading Standards guidance adds that "checks on the system should be also be recorded" ([Nottinghamshire CC](https://www.nottinghamshire.gov.uk/media/109053/foodduediligencebusinessinformation.pdf)). No official source sets a standard for electronic food records. Practitioner consensus, which the earlier plan already follows, asks for four things. Each check should carry an authenticated person and a server timestamp. Missed checks should be written down as Missed rather than left blank. Corrections should be appended with a reason, never silent overwrites. And manager reviews should be records too. Two additions come from this research. First, store the **device completion time and the server receipt time separately**, as Trail does, so a late sync never looks like a late check. Second, record a **4-weekly review** per site, because that is the SFBB pattern ([GOV.UK SFBB](https://www.gov.uk/government/publications/safer-food-better-business-sfbb/safer-food-better-business-sfbb)). A run of perfect readings, all exactly 3°C, invites suspicion. Honest gaps with logged fixes are more credible. That is practitioner opinion, not law.

**Retention needs a second look.** The earlier plan used a 2-year retain-only policy, following HANDOFF §8a. Prosecutions under the Food Safety Act must start within **three years of the offence** (or one year from discovery, whichever is earlier) ([legislation.gov.uk s.34](https://www.legislation.gov.uk/ukpga/1990/16/section/34)). Personal-injury claims, which include food poisoning, have a 3-year limitation period (community: [Penningtons Manches Cooper](https://www.penningtonslaw.com/insights/time-limits-for-bringing-a-personal-injury-claim-what-you-need-to-know/)). The ICO requires a justified, documented period ([ICO](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/)). **Recommendation:** keep daily checklist records, including day PDFs, for **3 years**, with the reason written in the retention schedule. Check this with Maginhawa's insurer, whose policy wording may ask for longer. Record staff by Entra ID and display name rather than drawn signatures, frame photos to exclude people, and tell staff in the privacy notice that checklist activity may be shown to EHOs and insurers.

Everything else in the earlier plan stands. ## Conclusion

The question "Excel, folders or lists?" turns out to be two questions: where the app writes, and where people look. They have different answers. The write side needs item-level concurrency, app-only access and indexed queries, and only lists provide all three in SharePoint. The read side needs something a tired manager can open on a phone at 23:30 and an inspector can take away. That is a PDF in a folder named after the restaurant, which no live query can beat. Treating the files as **generated, read-only and rebuildable** solves the usual problem with keeping two copies. Nobody edits the copy, so it can never drift from the record, and a failed night repairs itself the next night.

The most consequential change from the earlier plan is not a new component. It is a date. Indexes on SharePoint Online must exist before a list reaches 5,000 items, which for the answer list is within its first week, not its third. That turns index creation from a go-live checklist item into part of the provisioning script, and a list created by hand in the browser before the script runs is a risk. The second change is cultural rather than technical. The evidence from inspectors and the courts rewards records that show their gaps, so the design should make Missed days, late syncs and corrections easy to see, in the app, in the PDF and in the EHO pack.
